# Cairn

Cairn turns a plan document a human wrote into a graph of verified, concurrent work.

Cairn generates workflows for **Dagu**, an external DAG engine; a `dagu` binary on PATH is
what runs them. "The engine" throughout these documents means Dagu. Cairn's own code is
Python 3 with no third-party imports.

## Install

You need **Python 3.11 or newer**, **git**, and the **Claude Code CLI** a step runs its
agent through — the subscription or API key you already use with it is the only credential
in the picture, and Cairn never touches it. macOS and Linux are the supported platforms;
on Windows, use WSL, because every path Cairn resolves and every signal it sends is a POSIX
one and nothing here has been measured against the alternative.

**1. The engine, in one command.** The installer resolves the right asset for the platform,
downloads the release's `checksums.txt` and verifies the archive against it before
extracting:

```sh
curl -fsSL https://raw.githubusercontent.com/dagu-org/dagu/main/scripts/installer.sh \
  | bash -s -- --version v2.18.2 --service no
```

The version is pinned and the pin is deliberate. The engine's _input_ format is well
governed, but its run-state file — the thing every report is read out of — is an internal
struct with integer enums, no schema and no conformance test. The pin is what stops a
reporter reading nonsense. Cairn refuses to run against any other version and names both in
the refusal, rather than drifting the emitted format silently. Moving the pin is a manual
judgement: change `ENGINE_VERSION` in `cairn/workflow/schema.py`, re-record the fixture
corpus, and run the suite.

The installer puts the binary in a directory it adds to your `PATH`; `--install-dir <path>`
overrides that. `--service no` is not optional advice: a one-shot run needs no daemon, no
database and no scheduler, and the scheduler's retry scanner re-executes failed runs across
the whole machine — which for Cairn means re-running agent sessions that already changed a
repository.

**2. Cairn.** The checkout is the whole artifact — the package, the skill's documents and
the fixtures — and nothing in it reaches outside itself:

```sh
git clone https://github.com/CRJFisher/cairn.git && cd cairn
python3 -m pip install -e .     # optional: puts a `cairn` executable on PATH
```

The install is optional because the package has no dependencies: `python3 -m cairn` works
from the checkout, and a generated workflow uses neither path — it names an immutable
snapshot of this package, copied under the digest of its content when the workflow was
authored, so a run executes the Cairn it was generated by whatever happens to this
directory afterwards.

**3. The engine's machine-wide configuration.** Dagu writes `~/.config/dagu/base.yaml` on
the first invocation of any of its commands, and every workflow on that machine inherits it
— including a cron catch-up window armed at `6h`, which replays every slot a stopped
scheduler missed. Cairn owns the two fields it depends on:

```sh
python3 -m cairn supervise base-config --disable   # writes retry and catch-up off
python3 -m cairn supervise base-config             # asserts them, changes nothing
```

It edits rather than creates, verifies its own write, and refuses a file it cannot read
exactly. Until it has run once, `cairn schedule start` refuses with `base_catchup_enabled`.

**4. The skill.** Cairn is driven by typing `/cairn` in Claude Code, which finds it by its
directory. Register this checkout as a user-level skill:

```sh
mkdir -p ~/.claude/skills && ln -s "$PWD" ~/.claude/skills/cairn
```

A symlink rather than a copy, so the registered skill and the checkout are the same thing.

**5. Check it, starting nothing.** None of these launches a server, a scheduler or a run,
and none of them spends anything:

```sh
dagu version                              # 2.18.2
claude --version                          # the agent installation a step's session runs as
ls -l ~/.claude/skills/cairn/SKILL.md     # discovery: the registered skill is this checkout
python3 -m cairn supervise base-config    # the engine's config carries Cairn's values
python3 -m scripts.worked_example         # the example below; exits 3
```

Run them from the checkout. Nothing above needs the engine's server, and none of these
starts one.

**6. Author and explain a minimal plan, before anything is offered.** A plan this repository
ships, authored into a scratch repository and then explained. No session opens, no money is
spent, and the only thing written is the scratch repository's own admin directory:

```sh
mkdir -p /tmp/cairn-first && git -C /tmp/cairn-first init -q
python3 -m cairn plan report fixtures/plans/single-step/graph.json \
  --source-root fixtures/plans/single-step
python3 -m cairn workflow author fixtures/plans/single-step/graph.json \
  --repository /tmp/cairn-first --source-root fixtures/plans/single-step
python3 -m cairn explain workflow --plan single-step --repository /tmp/cairn-first
```

The parse report is what a person is shown and waits on in the real authoring conversation:
every step's task in full, the engine id beside the name the plan gave it, every dependency
with the words behind it, and everything left out with its cause. `workflow author` then
writes the definition and puts it through the engine's own `validate` and `dry` — which is
why `dagu` has to be installed for this step — and `explain workflow` says what running it
would do, step by step, having started nothing.

**That last line is the shape of every offer.** Cairn tells you what it would do and waits;
the first thing that costs anything is a run you ask for by name.

### Every path, and where it comes from

Nothing is configured and nothing is assumed from the shape of one person's machine. Each of
these is resolved at invocation, derived from something that was, or asked of the engine:

| Path                           | Resolved from                                                                      |
| ------------------------------ | ---------------------------------------------------------------------------------- |
| the target repository          | the request — never the directory the conversation is in                           |
| the plan document              | the request, and pinned by content when the workflow is authored                   |
| the worktrees root             | derived: `<repository>.cairn-worktrees/<plan>/<step>`                              |
| Cairn's own state              | the repository's git admin directory: `<repository>/.git/cairn/`                   |
| a run's records                | `<repository>/.git/cairn/runs/<run-id>`, carried to every step as `CAIRN_RUNS_DIR` |
| the Cairn a workflow runs      | `<repository>/.git/cairn/source/<digest-of-its-content>`, named by the file itself |
| the engine binary              | the name `dagu` on the invoking process's `PATH`                                   |
| the engine's data and DAG dirs | asked of `dagu config`, because they differ by platform                            |
| the engine's base config       | `$DAGU_HOME`, else the platform's user config directory — never the engine itself  |
| the view's address             | `CAIRN_VIEW_BASE`, then `DAGU_HOST`/`DAGU_PORT`, then `127.0.0.1:8080`             |

A generated workflow is the one deliberate exception, and it is a **per-machine build
product** by design: it names the package root, the repository and the runs root of the
machine it was authored on. Moving one to another machine means re-authoring it there, not
editing it.

## The worked example is the failing one

```sh
python3 -m scripts.worked_example
```

It reads a run recorded from a real engine. The engine's own verdict on that run is
`Succeeded`, exit `0`: every node either succeeded or was skipped, and none failed. Cairn
reads the same run and says this:

```
This run finished with exclusions. It is not a clean success.

1 of 2 steps contributed no verified work.

The engine calls this run succeeded and Cairn does not. Cairn's verdict is derived by
walking 9 nodes; the engine's own status is not read as a verdict.

  verdict              green_with_exclusions
  exit code            3
  engine's own status  succeeded
...
Excluded:
  subject: beta
    what: command completed
    cause: gate_indeterminate
```

A step said it was done; the gate could not confirm that anything landed; the step is
excluded, the cause is named, and the run is not a clean success. The command exits `3`.

This is the example on purpose. A demo where everything works demonstrates nothing that
distinguishes Cairn, because the engine would have agreed. It needs no engine, no agent
session, no network and no money: the run is `fixtures/runs/green-with-exclusions`, and
what renders it is the ordinary `cairn report` surface.

**Type `/cairn`, then say what you want.** Cairn is a skill and it opens only when it is
asked for by name: author a workflow from a plan, change one, run it, put it on a schedule,
read what a past run did, or ask what a workflow would do, what a verdict means, or why a
step was excluded. Six capabilities, all reachable by asking, and none of them needing a
second surface — though where the engine's own view is the better answer, the skill links to
it and says what it will never tell you.

Nothing else opens it. A sentence that describes the work without naming Cairn — "run my
plan", "schedule this nightly" — reaches whatever else is installed, and Cairn stays silent
rather than competing for it. A tool that commits to a repository is entered on purpose, and
naming it is the request.

Asking for a run starts it: the run id and the engine's view link come back at once.
[SKILL.md](SKILL.md) is where the rules for reading a request live.

**What is under it:** derive a plan graph from a plan's documents, validate it, and
read the parse report; answer the authoring conversation for a step whose plan named no
assertion; run a step under the committed-marker protocol so a resumed run skips work that
is already done, with the verify gate deciding what gets recorded; converge worktrees,
commit, land a wave's branches on the parent branch one at a time, and take and give back
the repository's run lock; generate a whole workflow file for a plan, refusing to write
one the engine would run into a silent failure; and read back what one run did with
`python3 -m cairn record build --run <run-id>`, as a presentation-free record whose verdict
is derived by walking every node — so a run the engine calls a clean success over a dropped
step reads as exactly that; give a plan a cron schedule and install it where a scheduler
watches, with `cairn schedule start` refusing on a machine whose retry or catchup policy
would re-execute failed runs; read any run at the engine's own view, from the address its
record carries — checked before anyone is sent to it, and served on request by one detached
`dagu server` that outlives the conversation asking for it; and render that record for a
terminal, a repository or a browser with
`python3 -m cairn report --run <run-id> --repository <path>`, which answers in order whether
it worked, what to do next, what needs attention, what each step did, and what shape the run was. Every run leaves that record whether anyone watched it or not.
And start a run of the definition that would execute, handing the engine exactly that one run.
Every agent session runs within the subscription's allowance: a step holds where the 5-hour
or weekly window is closed or nearly so, resumes a session that met the limit once the window
reopens, and ends `quota_held`, naming the moment, only where the wait is longer than a step
may make. A session that loses the model provider mid-turn is held the same way, probing for
up to 4 hours, and resumed where it left off once the provider answers
([docs/supervision.md](docs/supervision.md)).

and its authoring conversation, the branch topology, the merge step, the locks and repairs
that keep a run's writes under control, the generator and its preflight, the run model every

the skill that drives all of it.

## The quality gate

```sh
python3 -m unittest discover -s tests -t .   # roughly 1,600 tests
pyright                                      # strict, over the package, the tests and the scripts
```

Both run on every push and every pull request, in
[`.github/workflows/ci.yml`](.github/workflows/ci.yml), against the pinned engine installed
by the same one command the install path above names. The suite needs nothing installed
beyond Python and the engine; `pyright` is the one development dependency, pinned in
`pyproject.toml`'s `dev` group, and nothing that runs imports it.

The suite kills real processes, waits on real locks, serves real HTTP and drives a real Dagu
2.18.2, so it takes minutes rather than seconds; stray provider output during the run is
expected. It leaves no warnings, and a leaked file descriptor is a failure of the same kind
as a wrong answer, because a long run that exhausts the descriptor table fails somewhere
else entirely.

**One policy covers every suite that needs the engine: a missing `dagu` fails it.** The
defects these suites exist to catch are the ones that otherwise report success — a run the
engine calls clean over a step that never ran — so a silent skip would make the machine
with no engine the machine where everything passes. `CAIRN_SKIP_ENGINE_TESTS=1` is the one
way to pass without one, and what it buys is a record that the run did not check it.

## Housekeeping

The engine owns its own retention, and Cairn invents none:

```sh
dagu rm --history --older-than 30d <plan>   # run history older than a duration
dagu prune-artifacts --older-than 7d        # artifact directories no surviving run points to
```

Cairn's own command line is internal: the skill, generated workflows and tests invoke it,
its arguments carry no promise to anyone else, and nothing a person needs to do requires
learning them — the commands named above are what is under the skill, not a surface. Its
`--help` says so too, and names `/cairn`, because going looking for a command line is how
somebody who did not build this arrives at the wrong door.

**The engine's command line is a different matter.** You already have it for your other
jobs, and these are the verbs worth pointing at a Cairn plan:

| Command              | For                                                       |
| -------------------- | --------------------------------------------------------- |
| `dagu server`        | the view: a running graph, live step state, logs, timings |
| `dagu status <plan>` | whether a run is going, without opening a browser         |
| `dagu history`       | every run of a plan, without opening a browser            |

One is refused rather than useful: **never `dagu retry`**. Re-running a plan is the whole
recovery story, a continued occasion is what makes it cheap, and a retry reuses the run
identity in a way Cairn's own recovery already handles.

## Security posture

Every claim here is measured against Dagu 2.18.2 on the machine this was built on, not
inferred from the engine's documentation.

**What is closed.** The engine's server binds loopback only. Its API rejects
unauthenticated requests. Cross-origin requests are refused outright — a preflight from a
foreign origin answers `403 cross-origin request denied` — so a page in your browser cannot
drive the engine. Framing is blocked. Webhook tokens are enforced. Secrets on disk are
`0600`.

**The trust boundary is the user account, not the server.** Every hazard above concerns the
_API_. A local process does not need the API: it can run `dagu start` against any DAG file
directly, or read the token secret as the same user. Anything running as you can do
anything you can do, and no posture of the engine's closes that. Saying so plainly is more
honest than a security section that implies the API's authentication protects the
repositories a trigger mutates.

**A server Cairn starts is a server Cairn has claimed.** The engine's authentication begins
unclaimed, and the first local process to reach its setup endpoint becomes administrator —
when this was measured, a shell `curl` beat the human to it. So `cairn view start` claims
the account in the same breath as starting the server: it creates the user `cairn` with a
password minted from the platform's entropy source and prints it once. Cairn keeps no copy;
the engine keeps its own hashed one. An account already claimed is reported as held. A
claim that cannot be made at all stops the server Cairn just started — a claimed server or
no server, and no third end state.

**Cairn holds no credential, by construction rather than by policy.** A step runs the agent
installation you already authenticated — in the measured case a subscription login through
the OS keychain, with no `ANTHROPIC_*` variable anywhere in the step's environment. Nothing
is minted, stored, transported or prompted for. An API key remains available through the
same binary's normal precedence and needs no support here; the moment Cairn put a token in
its own environment it would be handling a credential. The view's administrator password is
the one secret Cairn ever mints, it is handed over in the sentence that creates it, and it
is written nowhere.

**Two outbound behaviours are disclosed rather than defended.** The engine's server checks
for a newer version on startup and renders an update banner; set `check_updates: false` in
the engine's own `config.yaml` to stop it. And an agent step's blast radius is bounded by
its deny list and its timeout and by nothing else — an allowlist is a floor, not a ceiling,
because the effective policy unions the step's grant with the operator's own settings and
the agent's built-in read-only judgement.

**The licensing boundary.** Dagu is GPL-3.0-or-later. Cairn invokes it as a subprocess and
never imports its Go API, which is what keeps GPL obligations off this artifact. Keep it
that way: linking the engine's code into Cairn, rather than running its binary, would cross
the boundary.

## What is read when it is installed

Measured by `python3 -m scripts.measure_surface`. Tokens are an estimate at 4 characters each, not a tokenizer's count.

| Read                          | What                                   | Characters | Lines | Tokens (est.) |
| ----------------------------- | -------------------------------------- | ---------: | ----: | ------------: |
| when Cairn is named           | the skill's description                |      `211` |   `1` |          `53` |
| when Cairn is named           | `SKILL.md`                             |    `13778` | `199` |        `3445` |
| when a capability is selected | `capabilities/running.md`, the largest |    `12338` | `183` |        `3085` |

**None of it is read unless asked for.** Cairn declares `disable-model-invocation: true`, so
its description stays out of a session's context until someone types `/cairn` — a session
that never names it reads nothing of it. The suite holds the skill and its description to
declared size limits.

Python 3.11 and the standard library, and nothing in this directory imports anything
outside it — which is what makes the checkout both the package and the skill, and makes
moving it the whole of packaging. The numbered documents these files cite — doc 05, doc 09
and so on — are the planning series this was built from; `planning/` here carries the ones
that are still open.
