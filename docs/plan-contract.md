# The plan contract

A plan is one or more Markdown documents a human wrote and committed. Their format is
unconstrained. Cairn reads them, derives a **step graph**, and runs a deterministic
validator over that graph. Interpretation proposes; the validator rules.

A step's `kind`, and what each kind becomes in the engine, is [step-kinds.md](step-kinds.md).

Two halves, deliberately separated:

| Half           | Who does it                    | Where it lives                           |
| -------------- | ------------------------------ | ---------------------------------------- |
| **Derivation** | an agent reading the documents | [plan-derivation.md](plan-derivation.md) |
| **Validation** | a deterministic script         | `cairn/plan/validate.py`                 |

Nothing generated by the derivation reaches the generator without passing the validator.

## The step record

One JSON object per step. Every field below is the whole vocabulary — an unknown field is
rejected rather than ignored.

| Field            | Required                         | Default                                  |
| ---------------- | -------------------------------- | ---------------------------------------- |
| `id`             | yes                              | —                                        |
| `slug`           | yes                              | —                                        |
| `title`          | yes                              | —                                        |
| `task`           | yes                              | —                                        |
| `command`        | for `command` steps              | —                                        |
| `command_type`   | for `command` steps              | —                                        |
| `deps`           | no                               | `[]`                                     |
| `verify`         | **key required, value nullable** | —                                        |
| `assertion`      | no                               | `null`                                   |
| `kind`           | no                               | `plan.default_kind`                      |
| `tools`          | no                               | `null`                                   |
| `scope`          | no                               | `once`                                   |
| `reads`          | no                               | `[]`                                     |
| `timeout`        | no                               | 3600s for `agent.*`, 600s otherwise      |
| `retries`        | no                               | `0` for every kind                       |
| `max_budget_usd` | no                               | 5.0 for `agent.*`, `null` otherwise      |
| `model`          | no                               | `sonnet` for `agent.*`, `null` otherwise |

- `id` is the engine identifier, matching `^[a-z][a-z0-9_]*$`.
- `slug` is the plan's own name for the step, verbatim, for display.
- `title` is the document's own heading or link text for the step.
- `task` is the change the document asked for.
- `command` is executable text quoted from the source document, never the prose `task`.
  `command_type` is `exec` or `wait_until`; the latter polls `command` until it succeeds.
- `verify` is nullable because absence is a recorded fact: the verify gate owns what
  happens then, and a command is never invented.
- `assertion` is the human's answer to a proposed verify command — `accepted`, `edited`,
  `authored` for one written where nothing was offered, or `declined` — with the proposal it
  answered and, on a decline, the reason. Its absence means
  nobody has been asked; a decline with `verify: null` is what makes a step unverified
  ([verify-gate.md](verify-gate.md)).
- `tools` is `null` for the provider's own policy; a list contains provider-translated
  deny patterns that narrow the blast radius.
- `scope` is one of `once`, `run`, `inputs`, `hourly`, `daily`, `weekly`, `monthly`.
- `reads` is required and non-empty only when `scope` is `inputs`.
- `timeout` is always present: I7 forbids an unbounded step, and the engine's own default
  is none. It bounds **each attempt**, not the step, so a step's worst case is every
  attempt plus every wait between them — which is how the run's maximum duration and the
  run lock's reclaim window are both derived. The plan document sets a step's own ("give
  it two hours", "at most fifteen minutes"); a plan that says nothing gets the kind's
  default.
- `retries` is `0` for every kind. Arbitrary shell is not assumed idempotent, and an agent
  failure is either a wrong task or a paid session that already changed the repository —
  neither is worth paying for twice. A rate limit is reported with the moment it clears
  rather than waited out ([supervision.md](supervision.md)). A plan may set its own value;
  the wait between attempts is 1s.
- `max_budget_usd` is the dollar ceiling of the one session an agent step opens, written
  into the emitted body as `--max-budget-usd`. It is always present on an agent step and
  always `null` on a command step, which opens no session: a session with no ceiling is
  the one thing an offer cannot price, so the emitter, the preflight and the offer each
  refuse a step without one. The default sits above any observed step cost; the plan
  document sets a step's own ("spend at most eight dollars on it").
- `model` is the model that session is pinned to, written into the emitted body as
  `--model` — which is how the run's record can name the model that did each step's work
  instead of recording whatever the environment chose. Always present on an agent step,
  always `null` on a command step. The default is the provider's stable alias for its
  mid-tier model; the plan document sets a step's own ("pin it to the opus model").

Every default lives in the field spec in `cairn/plan/schema.py` and is applied from there,
so a default stated in one place and applied in another cannot drift apart. `kind`,
`timeout`, `retries`, `max_budget_usd` and `model` are the five whose value depends on
another field, and `normalise` resolves those.

### Kinds a plan can author

`command`, and `agent.<provider>` matching `^agent\.[a-z][a-z0-9_]*$`. Nothing names a
specific provider except the run-level default and the provider dictionary, so adding a
provider is not a schema change and a new one gets the agent timeout rather than the
command one.

The rest of the step-kind vocabulary — `worktree`, `verify`, `commit`, `merge`, `lock`,
is emitted by the topology and the verify gate from the graph's own shape, so
it can never appear in a step record. A step that waits is a `command` calling
`cairn wait`.

### Every edge carries its own provenance and its own quotation

```json
{ "id": "config_schema", "origin": "declared", "evidence": "Task 01 (sentinel field)." }
{ "id": "bump_the_version", "origin": "derived", "evidence": "named for the version in `pyproject.toml`" }
```

`declared` means the document states the dependency; `derived` means the derivation
inferred it. **Both require evidence, and the evidence is a quotation from a source
document.** The origin changes what the report says about an edge; it never changes
whether the edge has to be justified. An edge with no evidence is a validation error, and
with `--source-root` an edge whose evidence appears in no document is an error too.

## The graph envelope

```json
{
  "cairn_graph_version": 2,
  "plan": {
    "slug": "worktree-hydration",
    "title": "Worktree Hydration",
    "source": "README.md",
    "sources": [{ "path": "README.md", "sha256": "…" }],
    "default_kind": "agent.claude",
    "id_collisions": []
  },
  "steps": [ … ],
  "omissions": [ { "slug": …, "title": …, "reason": …, "evidence": … } ],
  "questions": [ { "kind": …, "step": …, "question": …, "evidence": …, "proposed": … } ]
}
```

`sources` pins **every** document the derivation read, each by SHA-256, with `source`
naming the index among them. A plan written as a folder of numbered task documents pins
the folder's whole set, so a graph and a moved-on plan cannot silently disagree.

`reason` on an omission is one of `deferred`, `gated`, `already_done`, `out_of_scope`. An
omission's evidence is a quotation, checked like an edge's.

`kind` on a question is one of `unjustified_edge`, `missing_verify`,
`non_convergent_task`, `ambiguous_dependency`, `unresolved_reference`, `plan_gated`. A
question's evidence is not required to be a quotation — a question often records an
absence, and an absence cannot be quoted — with two exceptions, the readings the derivation
declares ([the declared readings](#the-declared-readings)): a `non_convergent_task`
question, and a `missing_verify` question carrying a `proposed` command, must each quote
the sentence the reading rests on, and the quote is rechecked verbatim.

`proposed` is the derivation's own offer for an unasserted step's end state — the command
the authoring conversation shows the author ([verify-gate.md](verify-gate.md)). It may sit
only on a `missing_verify` question, and it is never written into `verify`: only an answer
is a decision.

## Identifiers

**Step ids** are sanitised from the plan's own name for the step: lower-cased, a leading
ordinal dropped, every non-alphanumeric run collapsed to `_`, and a leading `s_` added when
what remains cannot start with a letter. The engine rejects a hyphenated step id outright,
so this is a constraint, not a preference. The plan's own name survives in `slug`, so the
report names steps the way the plan does while the emitted YAML names them the way the
engine requires.

**Collisions** are broken positionally: the first occurrence keeps the plain id and later
ones take `_2`, `_3`. The assignment is stable across re-derivations of the same document.
Every break lands in `plan.id_collisions` and is printed in the parse report under
_Renamed to fit the engine_, so a rename is something the author sees rather than something
the graph absorbs.

**The plan slug** names the worktree parent, the workflow file, and the run record. It
derives from the documents' own location: a plan written as a folder is named by the folder,
a plan written as one document by the file. It matches `^[a-z0-9][a-z0-9-]*$` **and is at
most 40 bytes**, because the workflow file's name is what the engine reads as the DAG name
and a longer one is refused at load. Two rules keep it inside that bound, and both are
functions of the document's name alone:

- A name that opens with a task id and then a title — `task-381 - Report entry points…`,
  `TASK-381.4 …` — **takes the id**, which is the name every document in that plan already
  uses for the plan. The whitespace is what separates an id from a title, so a folder
  genuinely called `task-381-migration-plan` keeps all of itself.
- Any other name past the bound is **cut at the last hyphen inside it and carries an
  eight-character digest of the whole name**, so two documents that agree for the first
  thirty-one characters still derive two slugs and cannot adopt each other's worktrees.

The digest rides on every cut rather than only on one that collides. A slug that varied with
what is already on disk would be a different name before its worktree parent existed and
after, and re-deriving it would quietly re-point the plan at a different worktree, a
different workflow file and a different run record.

Before generation the slug must collide with nothing in the namespaces it enters;
`python3 -m cairn plan slug <path> --against <dir>…` takes those directories from their
owners, and this contract owns only the rule that they are all free. Two plans that derive
one slug — two documents claiming one task id — is a thing for a person to settle, and the
collision is what says so.

## The validator

```text
python3 -m cairn plan validate <graph.json> [--source-root <dir>] [--json]
```

Exit 0 when there are no errors, 1 when there are, 2 when the graph could not be read at
all. Warnings never fail the run. A malformed graph always produces a verdict — never a
traceback — because a caller cannot tell a crash from a rejection.

**Errors** (a graph carrying one never reaches generation):

| Code                    | Meaning                                                  |
| ----------------------- | -------------------------------------------------------- |
| `schema`                | a missing, unknown, mistyped, or out-of-vocabulary field |
| `graph_version`         | a graph from a version this validator does not speak     |
| `plan_slug`             | a plan slug outside the grammar, or past the engine's 40-byte bound on a DAG name |
| `no_sources`            | a graph pinning no document, so nothing can be rechecked |
| `source_not_pinned`     | an index document absent from `sources`                  |
| `duplicate_source`      | the same document pinned twice                           |
| `step_id`               | an id the engine would reject                            |
| `duplicate_id`          | two steps sharing an id                                  |
| `duplicate_slug`        | two steps the plan names identically                     |
| `unresolved_dependency` | a dependency naming no step in the graph                 |
| `self_dependency`       | a step depending on itself                               |
| `duplicate_dependency`  | the same edge declared twice                             |
| `unjustified_edge`      | an edge with no evidence                                 |
| `cycle`                 | a cycle, named step by step — a cycle is not a topology  |
| `empty_graph`           | no steps                                                 |
| `empty_task`            | a step carrying no task                                  |
| `timeout` / `retries`   | a non-positive timeout or a negative retry count         |
| `budget`                | an agent step with no positive dollar ceiling            |
| `model`                 | an agent step naming no model                            |
| `scope_inputs`          | `scope: inputs` with nothing in `reads`                  |
| `omitted_and_included`  | one name appearing as both a step and an omission        |
| `unknown_question_step` | a question naming a step that is not in the graph        |
| `unquoted_reading`      | a declared reading that quotes no words                  |
| `unassertable_proposal` | a proposed command that cannot fail, so asserts nothing  |

With `--source-root`, five more:

| Code                     | Meaning                                                                  |
| ------------------------ | ------------------------------------------------------------------------ |
| `missing_source`         | a pinned document that is not there                                      |
| `stale_source`           | a document that changed since the graph was derived from it              |
| `evidence_not_in_source` | an edge, omission or declared reading quoting words no document contains |
| `invented_verify`        | a verify command no document gives, with no answer behind it             |
| `invented_command`       | a command no document gives                                              |

**Warnings** (recorded, reported, never blocking):

| Code              | Meaning                                               |
| ----------------- | ----------------------------------------------------- |
| `missing_verify`  | a step nobody has been asked about                    |
| `unverified_step` | a step whose author declined an assertion for it      |
| `redundant_edge`  | an edge already implied transitively                  |
| `unused_reads`    | `reads` declared under a scope that never hashes them |
| `open_questions`  | questions the author has not answered                 |

Reachability is not among them. In an acyclic graph every step is reachable from some
dep-free root by construction, so a reachability check can only ever restate acyclicity.
A cycle short-circuits the remaining topology checks, because a cycle makes every other
answer about ordering meaningless.

## The declared readings

**No code in Cairn interprets natural language.** The agent deriving the graph is the only
thing in the system that has read the plan, so two of the graph's values are readings it
declares, each resting on a quoted sentence, and the validator checks the quote — a fact
about two strings — never the sentence's meaning.

**Convergence.** A step killed mid-work resumes into its own half-finished worktree, so a
task phrased as a blind append or a create-anew produces a duplicate the second time round.
**The convergent idiom is "bring X to a state where Y"** — it reads as an assertion about
the end state rather than an instruction to act, which is what makes it re-runnable. Where
a document's own action cannot be restated without changing what it asks for, the
derivation keeps the document's words and declares the duplication as a
`non_convergent_task` question, quoting the sentence it read; the author restates it, not
the derivation.

**A proposed assertion.** Where a document states a step's end state in prose and gives no
command, the derivation declares the command it would offer on the step's `missing_verify`
question, resting on the sentence the question quotes. The authoring conversation carries
that offer to the author ([verify-gate.md](verify-gate.md)); nothing writes it into
`verify` but an answer.

Both declarations are held to their quotes: one quoting nothing is `unquoted_reading`, one
quoting words no document contains is `evidence_not_in_source` under `--source-root`, and a
proposed command that cannot fail is `unassertable_proposal`.

## The parse report

```text
python3 -m cairn plan report <graph.json> [--source-root <dir>] [--out <path>]
```

What Cairn understood, for a human to confirm before anything is generated: each step's
kind, scope, verify command, timeout, dollar ceiling and model; **what each step is asked
to do**, in full; every
dependency marked declared or derived with the words that justify it; the waves the
dependencies allow; what was left out and why; any id the engine forced a rename on; and
the questions the author has to answer.

A graph with a cycle or an unresolvable dependency gets no wave list. A plausible-looking
ordering for a graph that has none would show the author concurrency the plan never had.

## The fixture corpus

`fixtures/plans/<name>/` holds a plan's documents, the golden `graph.json` derived from
them, and `expect.json` naming the validator's verdict. Fifteen plans: a linear chain, a
two-way fan-out, a multi-wave plan, a single-step plan, a plan mixing kinds and scopes, a
plan declaring no dependencies, a plan connecting nothing at all, a plan whose every step
is already done, a plan with no verify commands, a plan whose every task the derivation
declared non-convergent, three plans each carrying one failure the validator must name, and
two real plans copied verbatim from this repository's `.planning/` tree.

Every fixture is validated twice: against the graph alone, and with `--source-root`, which
rechecks every pin and every quotation against the documents themselves.

Six of these plans are also the recorded inputs to `fixtures/workflows/`, so a change to one
of their graphs changes an emitted file too ([workflow.md](workflow.md)).

Run everything with `python3 -m unittest discover -s tests -t .` from this directory.
